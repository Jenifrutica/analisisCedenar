\section{Introducción y Levantamiento de Requerimientos}
% ============================================================

\subsection{Contexto del Problema}

CEDENAR opera en el departamento de Nariño con recaudadores instaladores que recorren zonas urbanas y rurales tomando lecturas de medidores. El proceso depende de una terminal portátil que descarga los datos del sector antes de cada jornada y necesita conexión continua para funcionar. Cuando la señal cae o la pantalla se refresca por accidente, el dispositivo puede congelarse hasta 15 minutos y el operario pierde el avance del día.

Del lado del cliente, no existe canal formal para aclarar cobros ni reportar cortes de luz. La única opción es ir a la casa del recaudador instalador del barrio o mandar un mensaje por WhatsApp personal al técnico, sin recibir radicado ni seguimiento.

Este proyecto propone digitalizar ese proceso con dos productos: una app móvil offline-first para el operario de campo y un portal web para el cliente, con tres actores: cliente residencial, recaudador instalador y administrador.

\subsection{Historias de Usuario con Definition of Done}

\subsubsection{HU-005: Registro de lectura del medidor}

\textbf{Como} Personal de Campo, \textbf{quiero} registrar lecturas en mi ruta, adjuntar foto y enviar recibo digital, \textbf{para} eliminar el papel y reducir errores de digitación.

\begin{tcolorbox}[title=Definition of Done, colback=blue!5, colframe=cedenarblue,
  fonttitle=\bfseries\small]
\begin{itemize}\setlength\itemsep{2pt}
  \item Lista de predios visible al iniciar sesión
  \item Escaneo QR/barras identifica el medidor correcto en la ruta
  \item Motor de Validación de Consumo invocado al guardar
  \item Anomalía generada con estado \texttt{PENDIENTE} si hay inconsistencia
  \item Modo offline con estado \textit{Pendiente de Sincronización}; cambia a \textit{Sincronizada} al recibir HTTP 200
  \item Envío de recibo por WhatsApp y correo funcional
\end{itemize}
\end{tcolorbox}

\begin{lstlisting}[style=gherkin, caption={Criterios de Aceptación -- HU-005}]
Scenario: Identificacion del medidor por escaneo
  Given el operario tiene su ruta cargada
  When escanea el codigo QR del medidor
  Then el sistema selecciona el contador correcto
  And solicita digitar el valor en kWh del display

Scenario: Operacion sin conexion
  Given el operario esta en zona sin datos
  When registra lecturas durante su recorrido
  Then el sistema guarda con estado Pendiente de Sincronizacion
  And actualiza a Sincronizada cuando la API retorna HTTP 200

Scenario: Alerta por lectura anomala
  Given el operario ingresa el valor del medidor
  When el Motor de Validacion detecta inconsistencia
  Then genera Anomalia con estado PENDIENTE
  And muestra alerta antes de confirmar el guardado
\end{lstlisting}

\subsubsection{HU-003: Reporte de falla o daño eléctrico}

\textbf{Como} Cliente, \textbf{quiero} reportar un corte desde la app, \textbf{para} que el equipo técnico lo atienda y yo pueda hacer seguimiento con un radicado.

\begin{tcolorbox}[title=Definition of Done, colback=blue!5, colframe=cedenarblue,
  fonttitle=\bfseries\small]
\begin{itemize}\setlength\itemsep{2pt}
  \item GPS capturado automáticamente; fallback a \texttt{codigoContrato} si no hay señal
  \item Radicado único generado y almacenado en el módulo de mantenimiento
  \item Reporte enrutado al despacho técnico por zona geográfica
  \item Cliente notificado con número de radicado
  \item Log de auditoría en cada cambio de estado del radicado
\end{itemize}
\end{tcolorbox}

\begin{lstlisting}[style=gherkin, caption={Criterios de Aceptación -- HU-003}]
Scenario: Reporte con GPS activo
  Given el cliente accede a "Reportar falla" con GPS activo
  When completa el formulario y lo envia
  Then el sistema captura coordenadas automaticamente
  And genera radicado unico, enruta al despacho y notifica al cliente

Scenario: Reporte sin GPS
  Given el cliente no tiene GPS o lo ha negado
  When reporta la falla
  Then el sistema usa el codigoContrato para determinar la zona
  And genera el radicado y notifica igualmente
\end{lstlisting}

\subsubsection{HU-006: Registro y seguimiento de PQRS}

\textbf{Como} Cliente, \textbf{quiero} registrar una PQRS desde la app, \textbf{para} recibir respuesta formal sin ir a una oficina.

\begin{tcolorbox}[title=Definition of Done, colback=blue!5, colframe=cedenarblue,
  fonttitle=\bfseries\small]
\begin{itemize}\setlength\itemsep{2pt}
  \item Formulario disponible para cliente y Personal de Campo
  \item Clasificación automática por tipo (Petición / Queja / Reclamo / Sugerencia)
  \item Radicado y notificación por correo y WhatsApp al registrar
  \item Panel administrativo con filtros por estado y tipo
  \item Notificación automática al cliente al resolver el caso
\end{itemize}
\end{tcolorbox}

\begin{lstlisting}[style=gherkin, caption={Criterios de Aceptación -- HU-006}]
Scenario: Cliente registra PQRS
  Given el cliente ha iniciado sesion
  When completa el formulario y hace clic en "Enviar"
  Then el sistema genera radicado unico
  And notifica por correo y WhatsApp con el numero de caso

Scenario: Resolucion del caso
  Given la PQRS fue marcada como resuelta
  When el sistema actualiza el estado
  Then envia notificacion automatica por correo y WhatsApp
\end{lstlisting}

\section{Arquitectura Empresarial (ArchiMate)}
% ============================================================

El diagrama ArchiMate organiza la solución en tres capas:

\begin{itemize}
  \item \textbf{Capa de Negocio:} Operario de Campo y Administrador de Lecturas como actores. Procesos: asignación de rutas, toma de lecturas en campo, validación de consistencia y auditoría de anomalías/fraudes.
  \item \textbf{Capa de Aplicación:} App Móvil de Captura y Dashboard Web. Servicios de Autenticación, Registro de Consumo, Motor de Validación Histórica y Alertas Automáticas.
  \item \textbf{Capa de Tecnología:} Dispositivos móviles con GPS, red celular/datos con soporte offline, servidores cloud y base de datos relacional CEDENAR.
\end{itemize}

Cuando el Operario ejecuta la toma de lectura (Negocio), usa la App Móvil (Aplicación), que sincroniza los datos al Servidor Cloud via HTTPS/JSON (Tecnología). El Servidor Central CEDENAR se conecta por VPN dedicada con JDBC/SQL.

\subsection{Diagrama de Clases}

La clase abstracta \texttt{Persona} centraliza los atributos comunes de identidad. Heredan de ella \texttt{Supervisor}, \texttt{Cliente} y \texttt{RecaudadorInstalador}. Un \texttt{Cliente} tiene una o más instancias de \texttt{Contador}. Cada \texttt{Contador} compone un historial de \texttt{Lectura} con el atributo \texttt{esConsistente} y la enumeración \texttt{EstadoLectura}. Cuando \texttt{esConsistente = false}, se genera una \texttt{Anomalia} vinculada al \texttt{Supervisor} para evaluación con \texttt{evaluarAnomalia()}. El módulo comercial agrega \texttt{Factura} (desde una lectura válida), \texttt{Pago}, \texttt{PQRS} y \texttt{Radicado} (con coordenadas GPS).

\subsection{Diagrama de Máquina de Estados}

Ciclo de vida completo de una \texttt{Lectura}:

\[
\texttt{Nueva} \rightarrow \texttt{En captura} \rightarrow \texttt{Capturada local}
\]
\[
\rightarrow \begin{cases}
  \texttt{Pendiente de sincronización} & \text{sin señal} \\
  \texttt{En validación} & \text{con señal}
\end{cases}
\rightarrow \begin{cases}
  \texttt{Validada} \rightarrow \texttt{Sincronizada} & \text{si consistente} \\
  \texttt{Observada} & \text{si anomalía}
\end{cases}
\]

Desde \texttt{Observada}, el Supervisor puede aprobar, rechazar u ordenar una recaptura.

\subsubsection{Fase 2: Definir}

Tres grupos de problemas al cruzar los hallazgos: (1) resiliencia en campo (HG-01, 02, 03), (2) equipo del operario (HG-04, 05) y (3) canal formal para el cliente (HG-06, 07, 08).

\begin{tcolorbox}[title=Declaración del Problema (POV), colback=blue!4, colframe=cedenarblue]
Iván Diaz lleva 17 años tomando lecturas en Linares y depende de que haya señal en el momento exacto para no perder media jornada. Necesita una herramienta que guarde el progreso localmente y lo sincronice sola cuando vuelva la conexión.

Doña Marta no tiene canal formal para aclarar su factura ni reportar un corte. Cuando algo falla, tiene que ir físicamente a la casa del recaudador. Necesita un canal que le dé un radicado y le diga en qué estado está su caso.
\end{tcolorbox}

\paragraph{Hipótesis para piloto real}

\begin{itemize}
  \item Si la app es offline-first, los tiempos muertos por caídas de señal caerán de $\approx$15 minutos por incidente a menos de 30 segundos.
  \item Si la cola sincroniza sola, el operario dejará de llenar formatos a mano en al menos el 90\% de las jornadas y cerrará el sector completo en un solo día.
  \item Si el recibo va digital, la impresora deja de ser necesaria y los reclamos por recibos no entregados desaparecen.
  \item Si el cliente puede reportar fallas con radicado, el tiempo de respuesta del despacho técnico cae al menos un 25\% frente al canal informal actual.
\end{itemize}

\subsection{Lógica de Negocio en Código (Kotlin)}
% ============================================================

Se eligió Kotlin porque el prototipo es una app Android y Kotlin es el lenguaje oficial de Android desde 2017. El código se lee casi como pseudocódigo (\texttt{data class}, \texttt{when}, \texttt{copy}) pero es real y directamente portable. Cada función está trazada a una pantalla del prototipo y a un requerimiento del backlog.

El repositorio completo: \url{https://github.com/Jenifrutica/analisisCedenar}

\subsubsection{Función 1: Validación con semáforo}

Pantalla de origen: captura de lectura con indicador verde/amarillo/rojo.
Trazabilidad: RF-05, HU-005, \texttt{MotorValidacionService} (sección 3.2 de la wiki).

\begin{lstlisting}[language=Kotlin, caption={LecturaService.kt -- validarLectura()}]
// Compara la lectura nueva contra el historico del medidor.
// Desviacion > 50%: ROJO (anomalia grave).
// Desviacion 20-50%: AMARILLO (revisar antes de confirmar).
fun validarLectura(nueva: Int, historico: List<Int>): Semaforo {
    if (historico.isEmpty()) return Semaforo.VERDE
    val promedio = historico.average()
    val desviacion = (nueva - promedio) / promedio * 100
    return when {
        desviacion > 50 -> Semaforo.ROJO
        desviacion > 20 -> Semaforo.AMARILLO
        else            -> Semaforo.VERDE
    }
}
\end{lstlisting}

\subsubsection{Función 2: Guardado offline con cola de reintentos}

Pantalla de origen: ``Lectura guardada localmente'' (fondo verde).
Trazabilidad: RF-05, RNF-04, HU-005 criterio ``Operación sin conexión''.

\begin{lstlisting}[language=Kotlin, caption={LecturaService.kt -- registrarLectura() y sincronizarPendientes()}]
// Siempre persiste local primero. Nunca se pierde el dato.
// Si hay senal, sincroniza de inmediato.
// Si no, WorkManager reintenta en segundo plano al recuperarla.
fun registrarLectura(lectura: Lectura, hayConexion: Boolean): EstadoLectura {
    db.guardarLocal(lectura)

    return if (hayConexion) {
        sincronizarPendientes()
        EstadoLectura.SINCRONIZADA
    } else {
        // El estado PENDIENTE_SYNC dispara la pantalla verde del prototipo
        EstadoLectura.PENDIENTE_SYNC
    }
}

// Marca como SINCRONIZADA solo al recibir HTTP 200 (DoD HU-005)
fun sincronizarPendientes() {
    db.obtenerNoSincronizadas().forEach { lectura ->
        val exitoso = api.enviarLectura(lectura)
        if (exitoso) {
            db.marcarSincronizada(lectura.id)
            auditLog.registrar("LECTURA_SINCRONIZADA", lectura.recaudadorId, lectura.id)
        }
    }
}
\end{lstlisting}

\subsubsection{Función 3: Generación de radicado y reporte de falla}

Pantalla de origen: ``PQRS Registrado con Éxito'' -- el número \texttt{\#71906-3163-1682} visible en el prototipo define el formato.
Trazabilidad: RF-03, HU-003, HU-006, clase \texttt{Radicado} (sección 3.1 de la wiki).

\begin{lstlisting}[language=Kotlin, caption={RadicadoService.kt -- generarRadicado() y reportarFalla()}]
// Formato visible en la pantalla "PQRS Registrado con Exito": #71906-3163-1682
fun generarRadicado(tipo: String, zona: String, clienteId: String): Radicado {
    val numero = "#${(10000..99999).random()}-" +
                 "${(1000..9999).random()}-" +
                 "${(1000..9999).random()}"
    auditLog.registrar("RADICADO_CREADO", clienteId, numero)
    notificaciones.notificarCliente(clienteId, "Tu caso fue registrado: $numero")
    return Radicado(numero = numero, tipo = tipo, zona = zona)
}

// Si el dispositivo no tiene GPS o el usuario lo nego,
// la zona se determina desde el codigoContrato del cliente.
// Origen: HU-003 criterio "Reporte sin acceso a GPS"
fun reportarFalla(
    tipo: String,
    gps: Pair<Double, Double>?,
    clienteId: String,
    codigoContrato: String
): Radicado {
    val zona = if (gps != null) {
        determinarZonaPorGps(gps.first, gps.second)
    } else {
        determinarZonaPorContrato(codigoContrato)
    }
    return generarRadicado(tipo, zona, clienteId)
}
\end{lstlisting}
